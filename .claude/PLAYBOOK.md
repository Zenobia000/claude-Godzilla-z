# Playbook：這套組合拳怎麼打

> **與 [WORKFLOW.md](WORKFLOW.md) 的分工**：那一份管**結構**——流程圖、各入口的輸入與完成條件、context 邊界、三層協作模型，是唯一權威。
> 本檔管**用法**——實際跑一輪長什麼樣、在哪裡停、什麼時候跳過什麼。不重述結構，只在需要時連過去。

## 先選路，不要先開工

三條路，選錯比走慢更貴：

| 你手上的東西 | 走 | 為什麼 |
|---|---|---|
| 一個你**握得住**的小改動，還在驗證想法 | [路線 A：雛型速通](#路線-a雛型速通) | 硬閘與追溯在這階段是純負擔 |
| 需求清楚、要交給人驗收 | [路線 B：Pilot 正規一輪](#路線-bpilot-正規一輪) | 完整組合拳，每一步都留證據 |
| 想法太大，**連要問什麼都還不確定** | [路線 C：霧中探索](#路線-c霧中探索) | 直接開工會做出錯的東西，而且看起來很像對的 |

判準只有一句：**你能不能現在把「做完長什麼樣」講成一句話？** 講得出來走 A 或 B，講不出來走 C。

---

## 路線 A：雛型速通

**Action Skills 是可選入口，不是關卡。** 直接對話迭代，先能動、能驗證。

```
確認分支 → 講清楚要驗證什麼 → 做出最小可動的東西 → 跑起來看 → 決定打掉還是往下
```

這條路上**唯二**不能省的：

1. **先開分支**（`rules/git-workflow.md` 鐵律）。
2. **回不了頭的決策寫一則 ADR**——而且要過三條件閘：難以逆轉 ∧ 沒有背景會讓人困惑 ∧ 真實取捨的結果。缺一就不寫。

不必做的：追溯 ID、驗收條件、切片看板、owner 簽核。需求追蹤簿留 `DEC-*` 骨架列就好。

**什麼時候該離開這條路**：東西要給別人驗、或你開始記不住做過什麼決定。那是升 Pilot 的訊號。

## 路線 B：Pilot 正規一輪

以「新增訂單匯出功能」為例，走完整條線。**每個 `▸` 是一個 session 邊界。**

### ▸ Session 1 — `/intake`

讀你專案的來源（Excel、訪談紀錄），把需求種進 `requirements_tracker.xlsx` ①需求決策，**owner 決策欄位留空**。

**卡住時**：來源有洞、兩份來源打架、或根本沒有來源 → `/intake --questionnaire`。它產出一份 L1 問卷讓你拿去問業主。手法是「只問你答得出來的」——寄給誰、要拿回什麼；**不要反過來訪談你自己那些答不出來的問題**，逼自己猜等於把假設寫成來源。

**停在這裡。** 等 owner 在 ①需求決策簽核。這個等待可能是幾天——所以狀態必須活在追蹤簿，不是對話裡。

### ▸ Session 2 — `/specify`（**這一段全程不能中斷**）

owner 簽核後開新 session，一口氣走完：

```
需求 → FR/NFR → ACPT → BDD 場景 → 決定測試接縫 → SAD → ADR → 追溯
```

**步驟 5「決定測試接縫」是這一段的關鍵，也是最容易被跳過的。** 載入 `sunnydata-codebase-design`，套四條規則：沿用既有接縫優於新開、用能觀測到行為的最高接縫、越少越好（理想是一個）、要新開就開在最高點。

然後**停下來讓人確認接縫**。這是 checkpoint 不是註記——接縫定了才知道 `/deliver` 的測試往哪裡下針、`/verify` 的證據從哪裡來。

> **為什麼不能中斷**：這幾步互為前提。中途 compact，後面的切片會建立在被摘要過的推導上，錯誤一路傳下去。逼近 smart zone（~120k）就把當前結論寫進文件、開新 session 續作，**不要壓縮著跑完**。

### ▸ Session 3 — `/deliver` 第一次（拆切片）

`/deliver` 開場先看 `engineering_tracker.xlsx` ③ 切片看板。第一次跑通常是空的，所以進入拆解：

- **縱切**穿過所有層，不是橫切一層
- 每片**塞得進一個全新 context window**
- 每片宣告 **Blocked by**，只列真的擋住它的
- **prefactor 排最前面**（先讓改動變容易，再做那個容易的改動）
- 改共用型別這種**爆炸半徑很大**的，不要硬塞成一片——走 expand → migrate 分批 → contract

拆完**呈現編號清單讓人確認**：顆粒度對嗎？依賴邊對嗎？哪幾片該合併或再拆？點頭後才依賴順序寫進看板。

### ▸ Session 4..N — `/deliver` 每片一個 session

每片開新 context，重複：

```
讀前緣（待開始 ∧ 未認領 ∧ blocker 全完成）
   → 先寫認領，再動工
   → TDD at 已確認的接縫
   → sunnydata-code-review 兩軸過一遍
   → 寫看板：待驗證 ＋ 證據連結
```

**兩軸 review 不要合併看**：Standards（規範＋Fowler smell）與 Spec（漏做／多做／看起來做了但做錯）分開報、不排名。合併就等於讓一軸掩蓋另一軸——「規範全過但做錯東西」是最貴的失敗，混在一起就看不見了。

### ▸ Session N+1 — `/verify`

獨立 context 跑所有 gate，用實際命令輸出判定。**只有 `/verify` 能把切片寫成 `完成`**，而且要完整 PASS；`CONDITIONAL PASS` 不能升級。

## 路線 C：霧中探索

`/wayfind` 起手。它**只產決策，不產交付物**。

```
▸ Session 1（開圖）  命名終點 → 廣度掃描 → 建 ticket → 連依賴邊 → 派 research 子代理 → 停
▸ Session 2..N       一個 session 解一張 ticket → 寫答案 → 更新地圖 → 霧畢業成新 ticket
▸ 路清楚了            交棒：需求候選 → /intake；已拍板的決策 → /specify；就地改動 → /deliver
```

**最容易搞錯的兩件事**：

1. **把霧預先切成 ticket 大小。** 判準是「你現在能不能把問題**講精準**」，不是能不能回答。講不精準就留在「尚未成形」——一片霧將來可能畢業成好幾張，也可能一張都沒有。
2. **一個 session 想解好幾張。** 這是刻意的限制，不是效能瓶頸。狀態活在地圖裡，不活在 context window 裡。

**想直接動手的衝動，是「已經走到地圖邊界、該交棒」的訊號**，不是「可以加速」的訊號。

## 決策點速查

| 情況 | 動作 |
|---|---|
| 答案在**人**身上，不在任何文件裡 | `/intake --questionnaire`，別自己猜 |
| 講不出「做完長什麼樣」 | `/wayfind`，別開工 |
| 「該長什麼樣」爭不出結果 | 做一個丟棄式原型提高討論解析度；驗證過的決策折回真碼，原型丟到 throwaway branch 當證據 |
| 一片切下去發現塞不進一個 context | 切太粗，回去重切，不要硬做 |
| 需要清單外的新接縫 | 這是**範圍變更**，退回 `/specify`，不是實作細節 |
| `/specify` 逼近 smart zone | 寫下當前結論、開新 session，不要壓縮著跑完 |
| 追蹤簿有你不認得的未提交變更 | **停**，問人。跨 session 撞車 |
| 同目錄出現 `~$*.xlsx` | Excel 開著，**停**，請人關掉再寫 |

## 常見錯誤

| 反模式 | 為什麼壞 | 改成 |
|---|---|---|
| 一個 session 從 `/specify` 直接做到 `/deliver` 完 | 規格的推導與實作細節互相污染 | 邊界斷開，切片各自新 context |
| 跳過接縫確認直接寫測試 | 測試落在沒人同意的位置，refactor 就全垮 | 接縫是 `/specify` 的 checkpoint |
| 實作者自己把切片標 `完成` | 這正是驗證閘存在的理由 | 只有 `/verify` 能寫，且要完整 PASS |
| 雛型期就上追溯與硬閘 | 拖垮驗證速度，而且多半白做 | 走路線 A，升 Pilot 再補 |
| 為顯而易見的選擇開 ADR | 稀釋真正重要的那幾份 | 三條件缺一就不寫 |
| 平行 agent 同時寫追蹤簿 | xlsx 沒有原子寫入，結果是**損毀**不是衝突提示 | 唯一寫入者，子代理唯讀 |
| 為了「完整」預載整個 skill 庫 | 塞爆 context，模型反而變鈍 | 只載當前步驟要的 |

## 多 session 怎麼配

**平行安全的**：不同切片（依賴不相交）、research ticket、唯讀審查（`code-quality-specialist`、`security-infrastructure-auditor`）。

**平行不安全的**：任何要寫追蹤簿的——**只有主 session 寫**，子代理把結果回報回來統一寫回。

任何 git 寫操作前先驗 ref 沒被別處推進（`rules/git-workflow.md` 多 session 協調）。

## 這套組合拳目前沒被驗證的部分

誠實標記，避免照著跑卻撞牆：

- **切片大小判準**（「塞得進一個 context window」）是設計層估的，還沒實測校準。
- **xlsx 併發規則**能防單機多 session，但沒跑過真正的平行切片。
- **地圖 30 張的升級門檻**是估的。

第一次跑完整一輪時，記錄這三項的實際感受，回頭修這份 Playbook——它是用法文件，本來就該被實戰改寫。
