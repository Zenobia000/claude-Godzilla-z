# Playbook：這套 harness 怎麼用

> **與 [WORKFLOW.md](WORKFLOW.md) 的分工**：那一份管**結構**——三層怎麼運作、context 邊界、常駐約束。
> 本檔管**用法**——實際跑一輪長什麼樣、在哪裡停、什麼時候跳過什麼。不重述結構，只在需要時連過去。

## 先選路

三條路，選錯比走慢更貴：

| 你手上的東西 | 走 | 為什麼 |
|---|---|---|
| 一個你握得住的小改動 | [路線 A：直接做](#路線-a直接做) | 規劃流程在這個規模上是純負擔 |
| 一個功能，做完長什麼樣講得出來 | [路線 B：規劃一輪](#路線-b規劃一輪) | 切片與接縫先定，實作才不會漂 |
| 想法太大，**連要問什麼都還不確定** | [路線 C：先撥霧](#路線-c先撥霧) | 直接開工會做出錯的東西，而且看起來很像對的 |

判準只有一句：**你能不能現在把「做完長什麼樣」講成一句話？** 講得出來走 A 或 B，講不出來走 C。

---

## 路線 A：直接做

```
確認分支 → 講清楚要驗證什麼 → 做出最小可動的東西 → 跑起來看 → 決定打掉還是往下
```

**唯二不能省的**：

1. **先開分支**（`rules/git-workflow.md` 鐵律）。
2. **回不了頭的決策寫一則 ADR**——而且要過三條件閘：難以逆轉 ∧ 沒有背景會困惑 ∧ 真實取捨的結果。缺一就不寫。

不必做的：完整規劃、切片清單、覆蓋率門檻、文件。`VibeCoding_Workflow_Templates/` 是選用的，不是待辦清單。

**什麼時候該離開這條路**：你開始記不住做過哪些決定，或東西要交給別人接手。

---

## 路線 B：規劃一輪

**每個 `▸` 是一個 session 邊界。**

### ▸ Session 1 — 探索到切片（**這一段全程不能中斷**）

載入 `sunnydata-design`，一口氣走完 Phase 1 → Phase 2：

```
探索意圖 → 方案取捨 → 寫規格 → 檔案結構 → 決定接縫 → 切片 → 任務
```

兩個最容易被跳過、但決定後面順不順的步驟：

**決定測試接縫。** 載入 `sunnydata-codebase-design`，套四條規則：沿用既有接縫優於新開、用**能觀測到行為的最高接縫**、越少越好（理想是一個）、要新開就開在最高點。接縫定了才知道測試往哪裡下針。**先確認再寫第一個測試**，不是寫完再說。

**垂直切片。** 每片穿過所有層的一條窄路，不是某一層的全部。四條判準：完整、可獨立驗證、**塞得進一個全新 context window**、接縫已定。prefactor 排最前面。改共用型別這種爆炸半徑很大的，不要硬塞成一片——走 expand → migrate 分批 → contract。

> **為什麼不能中斷**：這幾步互為前提。中途 compact，切片會建立在被摘要過的推導上。逼近 smart zone（~120k）就把結論寫進計畫檔、開新 session 續作，**不要壓縮著跑完**。

### ▸ Session 2..N — 每片一個 session

```
新 context → 讀這片的計畫 → TDD at 已確認的接縫 → 跑測試 → commit
```

`sunnydata-testing` 的三個反模式在這裡最容易犯：

- **tautological** —— 斷言用跟程式碼一樣的方式重算期望值，必然通過，永遠抓不到 bug
- **horizontal slicing** —— 先寫完所有測試再實作，驗證的是想像中的行為
- **implementation-coupled** —— refactor 一動測試就垮，但行為根本沒變

### ▸ 收尾

`sunnydata-code-review` 兩軸過一遍，然後 `sunnydata-branch-lifecycle` 收 PR。

**兩軸不要合併看**：Standards（規範＋Fowler smell）與 Spec（漏做／多做／看起來做了但做錯）分開報、不排名。合併等於讓一軸掩蓋另一軸——**「規範全過但做錯東西」是最貴的失敗**，混在一起就看不見了。

## 路線 C：先撥霧

`sunnydata-wayfind` 起手。它**只產決策，不產交付物**。

```
▸ Session 1（開圖）  命名終點 → 廣度掃描 → 建 ticket → 連依賴邊 → 派 research 子代理 → 停
▸ Session 2..N       一個 session 解一張 ticket → 寫答案 → 更新地圖 → 霧畢業成新 ticket
▸ 路清楚了            交棒 sunnydata-design（此時問題已經握得住了）
```

**最容易搞錯的兩件事**：

1. **把霧預先切成 ticket 大小。** 判準是「你現在能不能把問題**講精準**」，不是能不能回答。講不精準就留在「尚未成形」。
2. **一個 session 想解好幾張。** 這是刻意的限制，不是效能瓶頸。狀態活在地圖裡，不活在 context window 裡。

**想直接動手的衝動，是「已走到地圖邊界、該交棒」的訊號**，不是可以加速的訊號。

> 這是這裡認知負擔最重的流程。已經握得住的功能走路線 B 就好——用錯地方只會拖慢。

## 決策點速查

| 情況 | 動作 |
|---|---|
| 答案在**人**身上，不在任何文件裡 | `sunnydata-questionnaire`，別自己猜 |
| 講不出「做完長什麼樣」 | `sunnydata-wayfind`，別開工 |
| 「該長什麼樣」爭不出結果 | 做一個丟棄式原型提高討論解析度；驗證過的決策折回真碼，原型丟掉 |
| 一片切下去發現塞不進一個 context | 切太粗，回去重切，不要硬做 |
| 要在計畫外的位置寫測試 | 那是新接縫，先確認再寫 |
| 規劃逼近 smart zone | 寫下當前結論、開新 session，不要壓縮著跑完 |
| 工作樹有你不認得的變更 | **停**，問人。可能是別的 session |
| 想開 ADR | 先過三條件閘，缺一不寫 |

## 常見錯誤

| 反模式 | 為什麼壞 | 改成 |
|---|---|---|
| 一個 session 從規劃做到實作完 | 規劃的推導與實作細節互相污染 | 邊界斷開，切片各自新 context |
| 跳過接縫確認直接寫測試 | 測試落在沒人同意的位置，refactor 就全垮 | 接縫是規劃階段的產出 |
| 橫切（先做完 schema 層再做 API 層） | 任何一片都無法單獨驗證 | 縱切，每片穿過所有層 |
| 為顯而易見的選擇開 ADR | 稀釋真正重要的那幾份 | 三條件缺一就不寫 |
| 為了「完整」預載整個 skill 庫 | 塞爆 context，模型反而變鈍 | 只載當前步驟要的 |
| 小改動也跑完整規劃 | POC 的價值就是快 | 走路線 A |
| 兩軸 review 合成一份排名 | 一軸掩蓋另一軸 | 分開報，不排名 |

## 多 session 怎麼配

**平行安全的**：不同切片（依賴不相交）、research ticket、唯讀審查（`code-quality-specialist`、`security-infrastructure-auditor`）。

**平行不安全的**：同一個檔案的寫入、同一條分支的 git 操作。任何 git 寫操作前先驗 ref 沒被別處推進（`rules/git-workflow.md` 多 session 協調）。

## 什麼時候該換到 Pilot 線

這套 harness 刻意沒有：需求簽核閘、追溯 ID 主鏈、Excel 追蹤簿、證據閉環。它們在 POC 階段是純負擔。

**下面任一條成立，就該換到 Pilot 線**（`refactor/document-driven-ecosystem` 分支）：

- 需求由**別人**拍板，而且你需要證明某個範圍是誰在什麼時候核准的
- 要對外交付，驗收條件必須逐條可稽核
- 多人多團隊，「這條需求有沒有測到」需要查得出來而不是靠記憶
- 有法規或稽核要求

**先雛型 → 打掉 → 重構是正常路徑**，不是缺陷（見 `rules/thinking-boundary.md`）。別用 production 的標準卡住雛型，也別用雛型的標準交付 production。
