# 切片契約（Tracer-Bullet Slicing）

按需載入。`/deliver` 在「已核准規格 → 一批可獨立交付的切片」這一步讀本檔。切片看板的欄位、前緣查詢、認領協定與**併發寫入規則**在
[`docs/document-system/ticket-tracker.md`](../../../../docs/document-system/ticket-tracker.md)；本檔只管**怎麼切**。

## 切片規則

**縱切，不是橫切。** 每一片切穿所有層（schema → API → UI → 測試）的一條窄路，而不是某一層的全部。橫切的問題是沒有一片能單獨驗證——你得等所有層都做完才知道對不對。

四條判準，全中才算一片：

1. **完整**：穿過每一層的一條窄但完整的路徑。
2. **可驗證**：完成後能單獨 demo 或跑出證據，不依賴尚未完成的切片。
3. **塞得進一個全新 context window**：一個乾淨 session 讀得完它的規格、改得完它的碼、跑得完它的測試。塞不下就是切太粗。
4. **接縫已定**：它要驗的接縫在 `/specify` 步驟 5 已確認。需要清單外的新接縫 = 範圍變更，退回 `/specify`，不要就地開一個。

**Prefactor 先做。** 「先讓改動變容易，再做那個容易的改動」——重排、抽取、改名這類讓後續切片變好做的動作，自己成為一片，且排在最前面。

## 依賴邊（Blocking edges）

每一片宣告**哪些切片必須先完成**。沒有 blocker 的可以立即開始。

只列**真的擋住它**的：A 的介面 B 要用 → B blocked by A。單純「先做比較順」不是依賴，寫上去只會讓前緣變窄、平行度變差。

## 例外：Wide Refactor

**wide refactor** 是一個機械式改動，但**爆炸半徑**橫掃整個 codebase——改一個欄位名、換一個共用型別，一次編輯就打斷上千個呼叫點，沒有任何縱切能落地成綠燈。

不要硬塞成 tracer bullet，改排 **expand–contract**：

| 階段 | 內容 | 依賴 |
|---|---|---|
| **Expand** | 新形式加在舊形式旁邊，什麼都不壞 | 無 |
| **Migrate ×N** | 依爆炸半徑分批遷移呼叫點（每個 package／每個目錄一批），每批一片。舊形式還在，所以 CI 一路綠 | 各自 blocked by Expand |
| **Contract** | 確認沒有呼叫者後刪除舊形式 | blocked by 每一個 migrate 批次 |

連分批都無法自己維持綠燈時，保留同樣的順序，但讓這些批次共用一條整合分支，全部 block 住一張最終的「整合並驗證」切片——綠燈只在那裡承諾。

## 人工確認（拆完就停，不要直接開工）

把拆解結果以編號清單呈現，每片列出：

- **標題** — 一句話
- **Blocked by** — 哪幾片必須先完成
- **交付什麼** — 這片讓什麼端到端行為可以動（使用者視角，不是逐層實作清單）
- **接縫** — 在哪裡驗證

然後問三個問題，改到使用者點頭為止：

1. 顆粒度對嗎？（太粗／太細）
2. 依賴邊對嗎？每片是否只依賴真正擋住它的？
3. 有哪幾片該合併，或該再拆？

## 寫進看板

確認後才寫入 `engineering_tracker.xlsx` ③ 切片看板，**依賴順序寫**（blocker 在前），這樣 `Blocked by` 欄能引用到已存在的 `SLC-*`。

切片內容**不要**寫檔案路徑與程式碼片段——它們過期得很快。例外：原型產出的片段若比散文更精確地編碼了一個決策（狀態機、reducer、schema、型別形狀），就內嵌決策相關的最小部分，並註明來自原型。
