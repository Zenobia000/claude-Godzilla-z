# 切片看板（Excel 作為 Ticket Tracker）

`/deliver` 把已核准規格拆成垂直切片後，切片本身需要一個狀態機：誰擋誰、哪些可以現在動、誰認領了、結果是什麼。這份契約定義那個狀態機**住在哪、長什麼樣、怎麼寫才不會壞**。

## 1. 定位與 owner

切片是**工程層**產物（拆法由架構決定，不是需求決策），所以它住在工程追蹤簿：

| 項目 | 值 |
|---|---|
| 檔案 | `03_architecture/engineering_tracker.xlsx` |
| 工作表 | `③ 切片看板` |
| Owner | 架構師／RD lead（與該檔既有 owner 一致） |
| 上游 | `FR/NFR-*`、`SCN-*`（來自 `/specify`） |
| 下游 | `/verify` 的證據紀錄 |

一檔一個 owner 的規則不變——切片不進需求追蹤簿，需求 owner 不維護切片。

## 2. 為什麼是 Excel 而不是一堆 markdown

切片管理需要的四件事，Excel 全部原生支援，markdown 全部要靠掃目錄：

| 需要 | Excel | 一檔一 ticket 的 markdown |
|---|---|---|
| 前緣查詢（誰現在可以動） | AutoFilter | 掃全目錄逐檔解析 |
| 40 張切片的總覽 | 一個畫面 | 40 個檔案 |
| 依賴關係的視覺呈現 | 條件格式 | 無 |
| 狀態彙總 | 樞紐 | 無 |

**分工鐵律**：Excel 存「要排序、要篩選、要總覽」的；Markdown 存「要逐字讀」的。切片的**內容**（要建什麼、驗收條件）寫在規格文件裡，Excel 只放 ID＋狀態＋依賴＋一句話＋連結——與 [workbook-guide §5](workbook-guide.md) 的認知負載鐵律同一條。

## 3. 欄位

| 欄位 | 型別 | 說明 |
|---|---|---|
| `切片ID` | `SLC-NNN` | 主鍵。ID 模型見 [architecture.md §7.1](architecture.md) |
| `標題` | 文字 | 一句話說明這片讓什麼行為可以動 |
| `來源SCN` | 逗號分隔 | 這片實現哪些場景（橙色來源欄，同其他追蹤簿慣例） |
| `接縫` | 文字 | `/specify` 步驟 5 確認的接縫名。空值＝這片還不能開工 |
| `Blocked by` | 逗號分隔 `SLC-*` | 必須先完成的切片。空值＝可立即開始 |
| `狀態` | 下拉 | `待開始 / 進行中 / 待驗證 / 完成 / 封鎖` |
| `認領者` | 文字 | session 或人名。空值＝未認領 |
| `認領時間` | 時間戳 | 用於偵測 stale claim |
| `證據` | 連結 | `/verify` 產出的證據位置 |
| `備註` | 文字 | 一句話。長內容寫進規格文件並連結 |

## 4. 前緣查詢（Frontier）

**前緣 = 現在可以動手的切片**，定義：

```
狀態 = 待開始
∧ 認領者 為空
∧ Blocked by 列出的每個 SLC-* 狀態都是「完成」
```

在 Excel 就是三個 AutoFilter 條件加一次人工掃描依賴欄；切片數上百時，用一欄輔助公式把 `Blocked by` 的滿足與否算成布林再篩。

**切片大小的判準**：一片要能塞進一個**全新的 context window**。塞不下就是切太粗，回 `/deliver` 重切——不是硬做。

## 5. 認領協定

1. 動工前**先寫認領**（`認領者` + `認領時間`），再開始任何工作。順序反了，兩個 session 會撞同一片。
2. `認領時間` 超過 24 小時而狀態仍是 `進行中` 視為 **stale**，可由 owner 清空重新開放。
3. 完成後寫 `狀態=待驗證` 並填證據連結；`完成` 只能由 `/verify` 依實際證據寫入——agent 不得自行宣告完成（[golden-rules](../../.claude/rules/golden-rules.md) 第 4 條）。

## 6. 併發寫入規則（**這一節不遵守就會壞檔**）

xlsx 是 zip 封裝，**沒有原子寫入、沒有合併**。兩個寫入者同時動同一個檔案的結果是覆蓋或損毀，不是衝突提示。

1. **唯一寫入者**：只有**主 session** 寫追蹤簿。子代理與平行 agent 一律**唯讀**——它們把結果回報給主 session，由主 session 統一寫回。
2. **寫入前檢查 Excel 是否開著**：同目錄出現 `~$engineering_tracker.xlsx` 代表桌面版 Excel 持有鎖。**停止並請使用者關閉**，不要硬寫——硬寫的結果是使用者的編輯被無聲吃掉。
3. **Lock file**：寫入前建立 `engineering_tracker.xlsx.lock`（內容：PID、session id、UTC 時間戳），寫完刪除。發現既有 lock 且時間戳在 15 分鐘內 → 停止並回報；超過 15 分鐘視為 stale，可覆蓋。
4. **批次寫回**：一個 session 的所有狀態變更累積在記憶體，**收尾時一次寫回**。不要每改一個切片就開關檔案一次——每次開關都是一個撞車視窗。
5. **寫入前備份**：`cp engineering_tracker.xlsx engineering_tracker.xlsx.bak`，寫入失敗即還原。`.bak` 不入版控。
6. **跨 session 檢查**：寫入前跑 `git status -- <tracker>`；追蹤簿有你不認得的未提交變更 → **停止並詢問**（與 [git-workflow](../../.claude/rules/git-workflow.md) 的多 session 協調同一條規則）。

> **升級門檻**：當「唯一寫入者」開始擋住真正需要的平行度時，代表切片看板已經超出 Excel 的適用範圍。那時的正解是換成有原子寫入的 tracker（GitHub Issues／Linear），把 Excel 降級為**投影**（只讀報表），而不是想辦法讓多個 agent 同時寫 xlsx。這個轉換點要靠實測，不要預先優化。

## 7. 與追溯主鏈的關係

`SLC-*` 是**交付單位**，不是新的一條鏈：它掛在 `SCN-*` 之下，向下接 `/verify` 的證據。主鏈的唯一權威仍是 [architecture.md §7.1](architecture.md)；本檔不重述。

## 8. 誰讀這份契約

- `/deliver` — 拆切片、寫入看板、認領、更新狀態
- `/verify` — 讀前緣與待驗證項，寫入證據與 `完成`
- 任何要平行處理多個切片的編排 — 併發規則（§6）優先於效率
