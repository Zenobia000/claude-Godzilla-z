# 需求護身符：角色 × FR × NFR

> **版本:** v1.0 | **更新:** 2026-08-05 | **用途:** 每個專案開工前先過一遍；面試、訪談、Kickoff 可直接照念  
> **不是什麼:** 不是完整 SRS／SAD 範本（那些用 02–07）；這份只管「問對問題、權責不混」

---

## 0. 開場口訣（先背這四句）

1. **PM** 定「做不做／做什麼／多優先」  
2. **SA** 把業務拆成可驗證的系統需求（含 NFR **目標**）  
3. **架構師** 定系統怎麼長、NFR **怎麼達成**  
4. **SD** 把架構落到工程師明天能開工的契約  

**資料流：**

```text
PM：問題與範圍
  → SA：業務 → 可測需求（FR + NFR 目標）
    → 架構師：需求 → 系統形狀（邊界、選型、NFR 策略）
      → SD：形狀 → 可實作契約（API／DB／模組）
        → DEV：依契約實作
```

**語域對照**（見 `.claude/rules/language-register.md`）：

| 層 | 主要角色 | 語言 |
| :--- | :--- | :--- |
| L1 業務 | PM | 問題、價值、可觀察行為 |
| L2 橋接 | SA（＋架構師對外說明） | 業務詞 ↔ 工程詞並列 |
| L3 工程 | 架構師／SD／DEV | 介面、欄位、指令、失敗路徑 |

## 1. 四角色分工速查

| 角色 | 核心問題 | 管什麼 | 不管什麼 | 典型產出 |
| :--- | :--- | :--- | :--- | :--- |
| **PM** | 為什麼做？做給誰？做多少？ | 問題、價值、範圍、優先序、業務驗收、里程碑、Go/No-Go | 技術選型、模組切分、API 欄位 | PRD、Roadmap、User Story、驗收條件 |
| **SA** | 業務規則是什麼？系統要滿足哪些能力？ | 需求釐清、流程／用例、資料與規則、FR／NFR **目標**、邊界與例外 | 框架、部署拓撲、class 設計 | SRS／需求分析、Use Case、流程圖、需求對照 |
| **架構師** | 系統怎麼組成才撐得住？ | 系統邊界、元件切分、技術選型、NFR **實現**、整合與風險、ADR | 逐頁 UI 細節、每個函式怎麼寫 | SAD、C4、ADR、NFR 策略、介面原則 |
| **SD** | 工程師明天怎麼開工？ | 模組／類別、API 契約、DB schema、狀態機、序列圖、錯誤處理 | 產品優先序、業務要不要做 | SDD／LLD、API Spec、DB 設計、模組規格 |

### 決策權（打架時看這張）

| 決策類型 | 拍板者 |
| :--- | :--- |
| 做不做、優先序、業務驗收 | PM |
| 規則是否講清楚、需求是否可測 | SA |
| 回不了頭的技術形狀 | 架構師 |
| 介面／資料結構是否夠開工 | SD |
| NFR **目標值**嚴不嚴、要不要這條 | PM（價值）＋ SA（可測表述） |
| NFR **技術上可否達標、怎麼達** | 架構師 |
| 達不到時降標還是加預算 | PM（最終） |

### 最容易打架的四條邊界

1. **PM vs SA**：PM 說「要能退款」；SA 寫誰可退、時限、狀態、例外——**不寫**用哪個 DB。  
2. **SA vs 架構師**：SA 寫「要即時同步庫存」；架構師決定同步／非同步、一致性——**不重寫**業務規則。  
3. **架構師 vs SD**：架構師定「訂單服務＋事件匯流排」；SD 畫序列圖、定 topic／payload／重試——**不擅自改**服務邊界。  
4. **SD vs DEV**：SD 定契約與行為；DEV 實作。契約變了要回 SD／架構，不是現場改完再說。

### 一人多角（小團隊）

角色可以同一個人兼，**決策權仍要分開記**：

- 這條是「需求決策」還是「工程決策」？  
- 改 NFR 目標＝需求變更（回 PM／SA）；改實作策略＝架構／SD。  
- 需求決策（優先序、範圍、Gate、業務驗收）**不得**由工程或 AI 自動衍生。

## 2. SA vs 架構師：都有 NFR，差在哪

**一句話：SA 寫「要達成什麼」；架構師寫「怎麼達成、犧牲什麼」。**

| | SA | 架構師 |
| :--- | :--- | :--- |
| 角色 | NFR **需求** owner | NFR **實現** owner |
| 問的問題 | 業務／合規／營運要求系統「多好」？ | 用什麼結構／技術／取捨去達標？ |
| 產出 | 可驗證的約束與目標值 | 策略、元件選擇、ADR、量測方式 |
| 失敗樣子 | 「沒寫清楚要多快／多穩」 | 「寫了 99.99%，但架構撐不住或不能量測」 |

**同一條 NFR 範例（結帳要快）：**

| SA（需求層） | 架構師（設計層） |
| :--- | :--- |
| 場景：尖峰結帳 | 同步／非同步、快取、佇列、超時降級 |
| 指標：P95 < 2s | 瓶頸與容量規劃 |
| 範圍：含／不含哪些步驟 | 與成本、一致性的取捨（ADR） |
| 驗收：壓測情境與資料量 | 哪個 metric／alert 證明達標 |

**所有權流：**

```text
業務痛點／法規／SLO 期望
  → SA：NFR 條目＋目標值＋驗收情境   ← 需求契約
    → 架構師：能否達成？怎麼達成？取捨？ ← 設計回應
      → 做不到 → 回 SA／PM 改目標或範圍（不要硬撐）
```

**常見混淆（禁止）：**

- SA 寫「要用 Redis」→ 那是架構，不是 NFR。應寫「快取命中後讀延遲 < X」。  
- 架構師私自把 99.99 改成 99.9 → 這是需求變更，要回 SA／PM。  
- 兩邊各寫一份互不相干的 NFR 表 → 同一組 ID；SA 定目標，架構師對每條寫實現與驗證。

**模板落點：** [`05_architecture_and_design_document.md`](./05_architecture_and_design_document.md) 前段「非功能性需求」表＝目標；後段「NFR 實現」＝策略。

## 3. FR 要問什麼

**核心句式：**

```text
誰？在什麼情境？要達成什麼結果？規則與例外？怎麼算完成？
```

### 3.1 必問清單

**使用者與角色**

- [ ] 有哪些角色？（末端使用者、管理員、客服、外部系統）
- [ ] 各角色能做／不能做什麼？
- [ ] 有沒有「代操作」（A 幫 B 做）？

**目標與價值**

- [ ] 這個功能解決什麼問題？不做會怎樣？
- [ ] 成功長什麼樣？（可觀察結果，不要「系統要方便」）
- [ ] 跟現有流程差在哪？（手工／舊系統／Excel）

**主流程（Happy Path）**

- [ ] 從頭到尾步驟是什麼？
- [ ] 每步的輸入／輸出是什麼？
- [ ] 誰觸發？手動還是自動／排程／事件？

**業務規則**

- [ ] 計算怎麼算？（公式、四捨五入、匯率、稅）
- [ ] 狀態有哪些？怎麼轉？
- [ ] 哪些是不變量（必須永遠成立）？
- [ ] 誰有權改規則？改了舊資料怎麼辦？

**例外與邊界（最容易漏）**

- [ ] 失敗時怎麼辦？（重試、取消、人工介入）
- [ ] 重複送出怎麼辦？（冪等／防呆）
- [ ] 中途離開／逾時／部分完成呢？
- [ ] 空值、最大值、同時兩人改同一筆呢？

**資料（功能視角，不是 DB 設計）**

- [ ] 要顯示／輸入哪些欄位？必填？
- [ ] 來源是使用者輸入、系統帶入、還是外部系統？
- [ ] 哪些資料能改、哪些只能查？
- [ ] 歷史要不要留？要看得到誰改過嗎？

**權限與可見性**

- [ ] 誰看得到這筆資料？
- [ ] 欄位級權限有沒有？
- [ ] 跨組織／跨店／跨客戶的隔離規則？

**通知與副作用**

- [ ] 完成後要通知誰？
- [ ] 會連動改哪些別的資料／狀態？
- [ ] 要不要產生報表、憑證、流水號？

**跨系統**

- [ ] 要跟哪些系統交換什麼？
- [ ] 以誰的資料為準（SSOT）？
- [ ] 對端失敗時，本地要怎麼呈現？

**驗收**

- [ ] Given／When／Then 各一條主路徑
- [ ] 至少 2～3 條例外路徑
- [ ] 用什麼測試資料才算過？
- [ ] 「看起來做了但做錯」長什麼樣？

### 3.2 第一輪訪談：最小 8 題

1. **誰**會用這個功能？最常見的一種人是誰？  
2. 他現在怎麼完成這件事？痛在哪？  
3. 做完後，畫面上／現實中**必須出現什麼結果**？  
4. 有哪些**不能違反**的規則？  
5. 最常出錯的三種情況是什麼？期望系統怎麼處理？  
6. 哪些人**不能**看到或操作？  
7. 需要通知或連動其他流程嗎？  
8. 怎麼驗收才算「真的做對」？

### 3.3 每條 FR 建議欄位

| 欄位 | 問句 |
| :--- | :--- |
| ID | FR-xxx |
| 角色 | 誰？ |
| 觸發 | 什麼時候開始？ |
| 前置條件 | 開始前必須成立什麼？ |
| 主行為 | 系統做什麼？ |
| 業務規則 | 計算／狀態／限制 |
| 例外 | 失敗與邊界 |
| 結果 | 可觀察產出 |
| 驗收 | 過／不過判準 |
| 範圍外 | 這版明確不做什麼 |

### 3.4 壞答案 vs 好答案

| 壞 | 好 |
| :--- | :--- |
| 要有訂單管理 | 業務人員可建立訂單（客戶、品項、數量）；送出後產生訂單編號並進入「待確認」 |
| 用微服務做退款 | 客服可對「已付款且未出貨」訂單發起全額退款；成功後變「已退款」並通知客戶 |
| 系統要智慧一點 | 庫存不足時不可送出；提示缺料品項與可賣數量 |
| 支援各種狀態 | 狀態僅：草稿／已送出／已出貨／已取消；已出貨不可取消 |

### 3.5 FR 三條鐵律

1. **先結果、後畫面、最後技術** — 「要存哪張表」不是 FR 問題。  
2. **每條 FR 要能寫出至少一個驗收情境** — 寫不出來＝還沒問清楚。  
3. **明確寫「不做」** — 範圍外跟範圍內一樣重要。

**口訣：** 誰、在何時、做何事、依何規則、遇例外怎辦、完成長怎樣、怎樣算驗過。

## 4. NFR 要問什麼

**核心句式（每條都套）：**

```text
場景是什麼？ → 指標是什麼？ → 目標值多少？ → 怎麼驗／不過怎麼辦？
```

**每條再追問：**

1. 若不達標，業務損失是什麼？  
2. 用哪個數字判定過／不過？（沒數字就還不是 NFR）  
3. 在哪個環境量？（prod／壓測／UAT）  
4. 跟哪條 FR 綁在一起？（「結帳」不是「全站」）  
5. 跟別的 NFR 衝突時誰優先？（快 vs 一致 vs 成本）

### 4.1 必問清單（按類）

**效能**

- [ ] 哪個操作最痛？
- [ ] 可接受延遲？P50／P95／P99？
- [ ] 尖峰 QPS／併發？平常 vs 檔期？
- [ ] 資料量預期（現在、1 年後）？
- [ ] 慢了使用者會怎樣？

**可用性／可靠性**

- [ ] 能不能掛？掛多久可接受？（SLA／SLO）
- [ ] 維護窗能不能停機？
- [ ] 單點掛掉時，最小要保住什麼？（降級）
- [ ] RTO／RPO？

**擴展性**

- [ ] 成長從哪來？（使用者、資料、流量、地區）
- [ ] 哪一段會先爆？

**安全**

- [ ] 有哪些敏感資料？
- [ ] 誰能存取？角色／權限？
- [ ] 法規／稽核要求？
- [ ] 認證、鎖定、對外暴露面？

**資料**

- [ ] 保留多久？刪除／封存誰決定？
- [ ] 要不要稽核軌跡？
- [ ] 一致性要求？（強一致 vs 最終一致）
- [ ] 備份與還原演練？

**整合**

- [ ] 依賴哪些外部系統？掛了怎麼辦？
- [ ] 同步還是非同步可接受？
- [ ] 超時、重試、冪等的業務限制？

**可觀測／營運**

- [ ] 出事要在幾分鐘內發現？
- [ ] 必要的 log／metric／trace？
- [ ] 告警打給誰？升級路徑？

**易用／無障礙（有 UI 才重）**

- [ ] 目標裝置／瀏覽器／網路？
- [ ] 無障礙等級？多語系／時區？

**維護與變更**

- [ ] 發版頻率？能否零停機？
- [ ] 舊 API／相容性窗口？

**成本**

- [ ] 月預算上限？
- [ ] 寧願貴一點穩，還是便宜可降級？
- [ ] 流量暴衝時成本會不會失控？

**合規／稽核**

- [ ] 資料能不能出境／跨區？
- [ ] 要留哪些證據？變更要不要雙人核准？

**移植／鎖定（看情境）**

- [ ] 必須跑在既有雲／地端？
- [ ] 能不能綁特定廠商？

### 4.2 第一輪訪談：最小 8 題

1. 最不能慢的 3 個操作是什麼？各要多快？  
2. 尖峰大概多少人／多少請求？  
3. 系統掛掉最長能忍多久？  
4. 能不能丟資料？最多丟多少？  
5. 有哪些敏感資料與法規？  
6. 最關鍵的外部依賴是誰？掛了怎麼辦？  
7. 出問題要多久被發現、誰收告警？  
8. 預算／雲環境有沒有硬限制？

### 4.3 壞答案 vs 好答案

| 壞 | 好 |
| :--- | :--- |
| 要快 | 結帳 API P95 < 2s，尖峰 500 TPS |
| 要穩 | 月可用性 99.9%，計畫內維護另計 |
| 要安全 | 密碼雜湊、靜態資料加密、管理員操作留 audit log 180 天 |
| 要好維護 | 週發版、支援零停機、API 舊版至少養 90 天 |

### 4.4 最小實務規則

- **SA**：每條 NFR＝場景＋指標＋目標值＋怎麼驗。  
- **架構師**：每條 NFR＝策略＋影響哪些元件＋如何觀測＋取捨／ADR。  
- **對不上就升級**：目標與架構能力衝突時，先改需求或範圍，不要讓 DEV 默默扛。

## 5. 每專案開場檢查表（護身符本體）

開新專案或新 Epic 時，勾完再進詳細文件：

### A. 權責

- [ ] 誰是 PM／需求 owner？（業務驗收誰簽）
- [ ] 誰做 SA？（規則與可測表述）
- [ ] 誰做架構拍板？（不可逆技術形狀）
- [ ] 誰出 SD／契約？（API／DB／模組）
- [ ] 一人多角時，需求決策與工程決策有分開記嗎？

### B. 範圍

- [ ] 「做完長什麼樣」能講成一句話嗎？（講不出來先撥霧，別開工）
- [ ] 這版**不做什麼**已寫死？
- [ ] 成功指標／KPI 是什麼？

### C. FR（至少跑完 §3.2 八題）

- [ ] 角色、主流程、規則、例外、驗收都有答案
- [ ] 每條進範圍的 FR 至少一個驗收情境
- [ ] 沒有把實作細節（框架／表名）偷渡成 FR

### D. NFR（至少跑完 §4.2 八題）

- [ ] 效能、可用性、資料丟失、安全、外部依賴、觀測、成本有初步答案
- [ ] 每條重要 NFR 有數字或明確「這版不承諾」
- [ ] SA 目標與架構策略若衝突，已升級給 PM

### E. 下一步文件（按深度選）

| 階段 | 去做 |
| :--- | :--- |
| 雛型 | 問題＋可驗收行為＋最小設計；回不了頭的才開 ADR |
| Pilot | [`02` PRD](./02_project_brief_and_prd.md) → [`03` BDD](./03_behavior_driven_development_guide.md) → [`05` 架構](./05_architecture_and_design_document.md)＋[`04` ADR](./04_architecture_decision_record_template.md) |
| 契約開工 | [`06` API](./06_api_design_specification.md)＋[`07` 模組](./07_module_specification_and_tests.md) |
| 流程選擇 | [`01` 工作流說明](./01_workflow_manual.md) |

## 6. 一分鐘自測（送審前）

答不出來＝文件還沒好：

1. 這條是 FR 還是 NFR？owner 是誰？  
2. 過／不過的判準是哪個可觀察結果或數字？  
3. 若不做這條，業務損失是什麼？  
4. 跟哪條「不做」衝突了嗎？  
5. 架構若達不到，回誰改目標？
