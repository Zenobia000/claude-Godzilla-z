## 2. 需求決策主表

每一列是一個需求項的 owner 決策。工程 ID（`FR-*`/`NFR-*`）在 owner 核准**之後**才由 `/specify` 回填，作為往下游追溯的橋（L2）。

| 決策ID | 需求/VOC（業務語言） | 優先序 | 範圍 | 里程碑 | 業務驗收條件 | 商業例外/限制 | 決策狀態 | 決策者 | 日期 | 對應工程ID |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| DEC-001 | [用客戶語言描述要什麼、為什麼] | P0/P1/P2 | 納入/排除 | M1 | [owner 認定「做到了」的業務標準] | [法遵/合約/商業紅線] | 提案/已核准/延後/取消 | [姓名] | YYYY-MM-DD | FR-…（核准後回填）|
| DEC-002 | | | | | | | 提案 | | | |

**欄位說明：**

- **優先序**：owner 依商業價值定，不是由 ID 前綴或關鍵字自動判。若沿用系統建議值，須在此明確接受。
- **範圍**：本次發布**納入**或**排除**。排除項要留著（tombstone），不刪。
- **里程碑**：M1/M2/…，對應 Roadmap/WBS 的階段決策。
- **業務驗收條件**：用 owner 聽得懂的話寫「怎樣算通過」，不是工程測試步驟。
- **決策狀態**：只有 `已核准` 且有決策者與日期的項目，`/specify` 才能往下工程化。
- **對應工程ID**：核准前留空；核准後由 `/specify` 建立 `FR-*`/`NFR-*` 並回填，形成 `DEC → FR/NFR → ACPT → …` 追溯。

### 2.1 決策理由（思考軌跡）

記「為什麼」，不只結果——這是你的商業判斷軌跡，未來能回查當初怎麼想。**深思模式必填；速通模式可略或一句帶過**（見 [`.claude/rules/thinking-boundary.md`](../../.claude/rules/thinking-boundary.md)）。AI 在此只攤開選項與取捨，不替你決定。

| 決策ID | 理由 | 考慮過的選項 | 拒絕的替代與原因 | 當時的不確定 |

| DEC-001 | [為什麼這樣定] | [A / B / C] | [拒 B，因為…] | [還沒把握的地方] |

## 5. `/specify` 放行檢查（硬閘）

`/specify` 啟動前，逐項確認：

- [ ] 目標需求在**第 2 節**有對應列，且 `決策狀態 = 已核准`。
- [ ] 該列有**決策者**與**日期**（owner 簽核）。
- [ ] 優先序、範圍、里程碑非空，且不是未經接受的系統自動值。
- [ ] 若跨里程碑 Gate，**第 3 節**對應 Gate 為 `核准`。
- [ ] 商業例外/紅線已標記，工程契約需承接。

任一項不成立：**停止，退回 owner 決策**，不得由 AI 代填後續。
